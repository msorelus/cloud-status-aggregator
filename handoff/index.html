Overview

Multi-vendor cloud status aggregation, starting with Microsoft Azure

This service turns cloud provider health signals into one normalized, queryable feed — and turns a pull-only public feed into a push notification your platform can subscribe to. Microsoft Azure is the first vendor implemented. The data model, the change watcher and the webhook contract are vendor-neutral by design, so a second or third provider plugs in behind the same interfaces.

What it gives you

One normalized incident model

Three Microsoft sources reconciled into a single shape: global incidents, regional incidents, and planned maintenance — each with a tracking ID, status, impacted services and regions.

Change detection

The watcher polls on an interval, diffs against the last-seen snapshot, and emits only what actually moved: new, updated, resolved.

Signed webhook push

Deltas are POSTed to your endpoint with an HMAC-SHA256 signature. Microsoft publishes no push mechanism for the public status feed, so this layer supplies it.

Agent-ready via MCP

The same data is exposed as Model Context Protocol tools, so a Copilot or Teams agent can answer “is Front Door degraded right now?” without bespoke glue.

The signal that matters for a distributor

Microsoft publishes to the public Azure Status page only in three situations: broad impact across multiple services or regions, an issue that blocks access to the portal or Service Health itself, and broad impact where affected customers have not yet been identified. Everything narrower goes to the tenant-scoped Service Health blade instead. (Microsoft Learn — Azure Status overview)

Why that is the good news That publishing threshold is almost exactly the profile of an event that floods a support desk with tickets. The public feed is narrow, but it is narrow in your favour — it fires on the broad, multi-tenant events that generate call volume, and it does so without needing access to any customer's subscription.
Read this before you demo it

!What this does not do

The single most important design rule in this codebase: nothing is synthesized. If a source publishes nothing, the service reports “nothing published” — never “verified healthy.” Absence of an incident is not evidence of health, and the API will not pretend otherwise.

It does notBecause
Confirm a service is healthy The public feed only reports problems. Silence means “no broad incident published,” which is a different claim.
See tenant-specific incidents without access Narrow-impact events land in the customer's own Service Health blade. Reaching them requires delegated access to that tenant.
Predict or detect outages independently It is an aggregator, not a monitor. It reports what vendors publish; it runs no synthetic probes.
Replace Service Health alerts inside a subscription For a subscription you own, native Service Health alerts are richer and lower-latency. This fills the gap outside those boundaries.
Never say this “Azure Front Door is healthy in East US 2.” The correct statement is “no incident affecting Azure Front Door in East US 2 has been published.” The API responses are worded this way on purpose; keep that wording when you surface them in your own UI.
How it fits together

▢Architecture

Deployed shape in Azure

No secrets in configuration The webhook signing key is stored in Key Vault — that is where you read it back, rotate it, and audit access to it. It reaches the container as a platform-managed Container Apps secret, and the WEBHOOK_SECRET environment variable is a secretRef, never a literal value. The key travels as a @secure() template parameter, so it is not logged, not readable from deployment history, and never appears in deployment output.

2Quick deploy — azd up

From the repository root. One command provisions the resource group, container registry, managed identity, Key Vault, Container Apps environment and the app, builds the image inside the registry, rolls it out, and prints the URLs. 

# Name the environment. This names the resource group (rg-<name>) and tags every resource.
azd env new cloud-status-dev --location eastus2

# Generate a signing secret for the webhook (keep this — your subscriber needs it)
azd env set WEBHOOK_SECRET "$(openssl rand -hex 32)"

# Where change notifications should be POSTed (optional; omit to start read-only)
azd env set WEBHOOK_URL "https://tickets.example.com/hooks/cloud-status"

# Optional: subscriptions to also pull Service Health from

Without Azure Developer CLI

Some tenants cannot install azd. infra/deploy.sh drives the same Bicep templates with plain Azure CLI, in the same two passes — provision, build, then roll out the real image. 

export WEBHOOK_SECRET="$(openssl rand -hex 32)"
export WEBHOOK_URL="https://tickets.example.com/hooks/cloud-status"   # optional

./infra/deploy.sh cloud-status-dev eastus2

Or drive ARM directly. The template is subscription-scoped and creates its own resource group.

# 1. Provision (the app starts on a placeholder image)
az deployment sub create \
  --location eastus2 \
  --template-file infra/main.bicep \
  --parameters environmentName=cloud-status-dev location=eastus2 \
               webhookUrl="https://tickets.example.com/hooks/cloud-status" \
               webhookSecret="$WEBHOOK_SECRET"

# 2. Read back the registry the template created
RG=$(az deployment sub show -n main --query properties.outputs.AZURE_RESOURCE_GROUP.value -o tsv)
ACR=$(az deployment sub show -n main --query properties.outputs.AZURE_CONTAINER_REGISTRY_NAME.value -o tsv)
LOGIN=$(az deployment sub show -n main --query properties.outputs.AZURE_CONTAINER_REGISTRY_ENDPOINT.value -o tsv)

# 3. Build server-side with ACR Tasks
az acr build --registry "$ACR" --resource-group "$RG" \
  --image cloud-status-aggregator:1.0.0 --file Dockerfile .

# 4. Roll the real image out
az deployment sub create \
  --location eastus2 \
  --template-file infra/main.bicep \
  --parameters environmentName=cloud-status-dev location=eastus2 \
               apiExists=true \
               containerImage="$LOGIN/cloud-status-aggregator:1.0.0" \
               webhookUrl="https://tickets.example.com/hooks/cloud-status" \
               webhookSecret="$WEBHOOK_SECRET"
Why two passes The registry is created by the same template that runs the container, so on a first deployment the image does not exist yet. The app starts on a public placeholder, then the second pass swaps in your build. apiExists=true tells the template to read the running image back, so re-provisioning later never rolls your version backwards.

5Webhook contract

When the watcher detects a change it POSTs a single JSON body to WEBHOOK_URL. Only deltas are sent — a poll that finds nothing new sends nothing at all.

Request headers

HeaderValue
content-typeapplication/json
user-agentcloud-status-aggregator/0.1
x-aggregator-signaturesha256=<hex> — HMAC-SHA256 of the exact raw body, keyed with WEBHOOK_SECRET. Present only when a secret is configured.

Change kinds

KindFires when
newA tracking ID the watcher has never seen appears in the feed.
updatedA known ID's status, last-update timestamp, title or summary changed.
resolvedA known ID flipped to resolved, or dropped out of the feed entirely — Microsoft removes closed incidents, so disappearance is the resolution signal.
Restart behaviour The first poll after a start or redeploy primes the baseline and publishes nothing. That is deliberate: a restart must never replay incidents your subscriber has already processed. The trade-off is that a change occurring during a restart window is picked up on the following poll as an updated rather than a new.

If you cannot accept an inbound POST

Poll GET /api/status/changes instead. It returns the same delta set from the most recent poll, plus watcher health — poll count, last poll time, last delivery result and last error.

Do not skip this

6Verifying the signature

Compute HMAC-SHA256 over the raw request body bytes — not a re-serialized object — and compare in constant time. Reject anything that does not match. 

const express = require("express");
const { createHmac, timingSafeEqual } = require("crypto");

const SECRET = process.env.WEBHOOK_SECRET;
const app = express();

// Capture the raw body — signing must use the exact bytes we received.
app.use(express.json({ verify: (req, _res, buf) => { req.rawBody = buf; } }));

app.post("/hooks/cloud-status", (req, res) => {
  const received = String(req.get("x-aggregator-signature") || "");
  const expected = "sha256=" +
    createHmac("sha256", SECRET).update(req.rawBody).digest("hex");

  const a = Buffer.from(received);
  const b = Buffer.from(expected);
  if (a.length !== b.length || !timingSafeEqual(a, b)) {
    return res.status(401).json({ error: "bad signature" });
  }

  for (const change of req.body.changes) {
    // vendor tells you which provider this came from
    // correlate on issue.trackingId (Microsoft's ID) or issue.id (always present)
    console.log(req.body.vendor, change.kind, change.issue.trackingId, change.issue.title);
    // → raise / update / close the ticket in your ITSM system
  }

  // Always 2xx quickly; do the real work asynchronously.
  res.status(200).json({ received: req.body.changes.length });
});

app.listen(8080);

Three ways to get this wrong 1. Signing a re-serialized object instead of the raw bytes — key order and whitespace will differ and every signature fails. 2. Using == instead of a constant-time compare. 3. Doing slow downstream work before responding — return 2xx first, process after, or the watcher will log a delivery timeout.

Test your receiver before pointing production at it

# Craft a signed request by hand and confirm your endpoint accepts it
BODY='{"specVersion":"1.0","vendor":"microsoft-azure","counts":{"new":1,"updated":0,"resolved":0},"changes":[]}'
SIG="sha256=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$WEBHOOK_SECRET" -r | cut -d' ' -f1)"

/api/status/view refreshes on the same cadence as the watcher, pauses when the browser tab is hidden, highlights rows that arrived since the last render and raises a toast when something new appears. It has a manual Refresh now and a Pause control for demos where you need the screen to hold still.

For agents

8MCP tools

The aggregator speaks Model Context Protocol at /mcp, so Copilot Studio, a Teams bot, or any MCP-capable host can query it directly. Four tools:

ToolInputPurpose
get_active_incidentsnoneEverything currently published, grouped global / regional, with counts and source health.
get_regional_healthregionIncidents affecting a named region. Returns an explicit “nothing reported” note when the list is empty.
get_planned_maintenanceregion?, service?Maintenance windows, optionally scoped. Omit both for everything.
lookup_service_regionservice, region?“Is <service> affected?” — anywhere, or in one region if you pass one. Returns { impacted, incidentCount, incidents[], regionsAffected }.
Scope server-side — do not filter regions yourself Real Service Health rows frequently arrive with an empty impactedRegions and name the region only in the title — “End of Unplanned Maintenance for App Service in East US 2” is a live example from a real tenant. The tools match region against the incident text as well as the structured field. Any client that re-implements filtering on impactedRegions alone will silently miss live events. Pass region to the tool instead.
Why region is optional “Is Front Door having problems?” names no region, and it is one of the most common questions an agent receives. When region was mandatory, agents could not express that query and fell back to returning every unrelated incident — which reads to a user as a hallucination. Omit region to ask “anywhere”; the response echoes scope: "service-anywhere".
The honesty contract holds here too An empty result carries a note stating explicitly that it is not a positive health measurement. Agents built on these tools inherit the right wording instead of confidently telling a user that a service is fine.

Authentication is off by default — decide before you share the URL A default deployment accepts /mcp requests from anyone who knows the FQDN, which is fine for a pilot on non‑sensitive telemetry and nothing else. The server ships with Microsoft Entra ID bearer‑token validation built in; it is disabled until you set MCP_AUTH_ENABLED=true so that mock mode and the test suite run without a tenant. The mode is never silent — GET /healthz reports "mcpAuth":"entra" or "mcpAuth":"none", so you can always tell which one is live.

Container Apps built‑in authentication is not a shortcut here: it uses a browser redirect flow and does not serve the OAuth protected‑resource metadata that MCP clients discover, so switching it on tends to break the client rather than secure it. The app therefore validates tokens itself and serves its own /.well-known/oauth-protected-resource.

Turn on Microsoft Entra ID authentication

Two app registrations: one identifies the API (the audience tokens are minted for), one lets the editor sign a user in. Both are needed because Entra ID does not implement OAuth Dynamic Client Registration, so an MCP client cannot create its own identity on the fly the way the spec assumes — you supply the client ID in the editor config instead.

  1. Register the API and expose a scope. The requestedAccessTokenVersion: 2 patch matters: it is what makes Entra issue v2.0 tokens whose issuer matches the authority the client discovered.

      { \"appId\": \"$CLIENT_ID\", \"delegatedPermissionIds\": [\"$SCOPE_ID\"] },
      /* Visual Studio Code */
      { \"appId\": \"aebc6443-996d-45c2-90f0-388ff96faa56\", \"delegatedPermissionIds\": [\"$SCOPE_ID\"] },
      /* Azure CLI, so you can mint a token to test with */
      { \"appId\": \"04b07795-8ddb-461a-bbee-02f9e1bf7b46\", \"delegatedPermissionIds\": [\"$SCOPE_ID\"] }
    ]}
  }"
  4. Register the endpoint URL as a second Application ID URI. This is the step people miss, and it is why it comes after the first deploy — the URL does not exist until then. MCP clients that implement RFC 8707 send the endpoint URL as a resource parameter on the token request, and Entra will not issue a token for a resource it has never heard of. Read the warning below before skipping it. 
    APP_URL=$(azd env get-value SERVICE_API_URI)
az ad app update --id "$API_ID" \
  --identifier-uris "api://$API_ID" "$APP_URL/mcp"

az ad app show --id "$API_ID" --query identifierUris -o json
#   → ["https://<your-app>.azurecontainerapps.io/mcp", "api://<api-app-id>"]
  5. Enable it on the deployment and redeploy. The audience is the API's bare application ID, not the api:// URI — see the warning below. 
    azd env set MCP_AUTH_ENABLED true
azd env set MCP_AUTH_AUDIENCE "$API_ID"
azd env set MCP_AUTH_TENANT_ID "$(az account show --query tenantId -o tsv)"
azd up

curl -s "$(azd env get-value SERVICE_API_URI)/healthz"
#   → {"status":"ok","mock":false,"mcpAuth":"entra"}
  6. Point the editor at it. Add the oauth block to the server entry from the configuration above. On first use the editor opens a browser sign‑in against login.microsoftonline.com; the token is cached and refreshed from then on. 
    {
  "servers": {
    "cloud-status-aggregator": {
      "type": "http",
      "url": "https://<your-app>.azurecontainerapps.io/mcp",
      "oauth": { "clientId": "<public-client-app-id>" }
    }
  }
}
If the client fails with AADSTS9010010 Full text: “the resource parameter provided in the request doesn't match with the requested scopes.” The client asked for a token using RFC 8707 Resource Indicators — it sent resource=https://<host>/mcp next to the scope. Entra derives the resource from the scope and rejects the pair when the two disagree, so a scope of the form api://<guid>/status.read cannot be combined with an endpoint URL as the resource. The server therefore advertises scopes qualified with its own endpoint URL (https://<host>/mcp/status.read), which is what makes the registration step above mandatory. In VS Code this appears as Connection state: Error 401 immediately after a successful metadata discovery, with no sign-in window ever opening.

If you cannot add the identifier URI — some tenants restrict this — pin the old form with azd env set MCP_AUTH_SCOPES "api://<api-app-id>/status.read". Fully qualified values are passed through untouched. That works with clients that do not send a resource indicator, but not with VS Code.
The audience is the bare GUID, not the api:// URI A v2.0 access token carries aud as the API's raw application ID even though the client requested the scope as api://<guid>/status.read. Only v1.0 tokens use the api:// form. Setting MCP_AUTH_AUDIENCE to the URI rejects every request with a 401 after a sign‑in that looked completely successful, which is a miserable thing to debug. For the same reason the metadata advertises the fully qualified scope: a client that echoes back a bare status.read gets a Microsoft Graph token, which then fails audience validation the same silent way. The server accepts both aud forms defensively.

Verify authentication from the command line

Run this before involving an editor. It separates “the server is wrong” from “the client is wrong,” which is most of the work in diagnosing an MCP auth failure. 

APP_URL=$(azd env get-value SERVICE_API_URI)

# 1. No token must be refused, and must say where to authenticate.
curl -si -X POST "$APP_URL/mcp" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" -d '{}' | grep -i "^HTTP\|^www-authenticate"
#   → HTTP/2 401
#   → www-authenticate: Bearer error="invalid_token", ...,
#        resource_metadata="https://.../.well-known/oauth-protected-resource/mcp"

# 2. That metadata document must be readable WITHOUT a token.
curl -s "$APP_URL/.well-known/oauth-protected-resource/mcp"
#   → {"resource":"...","authorization_servers":["https://login.microsoftonline.com/<tid>/v2.0"],
#      "scopes_supported":["api://<api-app-id>/status.read"], ...}

# 3. A real token must be accepted.
TOKEN=$(az account get-access-token --scope "api://<api-app-id>/status.read" \
  --query accessToken -o tsv)
curl -si -X POST "$APP_URL/mcp" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
       "protocolVersion":"2025-06-18","capabilities":{},
       "clientInfo":{"name":"curl","version":"1"}}}' | grep -i "^HTTP\|mcp-session-id"
#   → HTTP/2 200  +  mcp-session-id: 6f2c...

Note that only /mcp is protected. The REST API and the dashboard stay open so the demo still works — if you need those locked down too, put the whole app behind Azure API Management or Front Door with a WAF, as described in Production hardening.

Confirm the handshake without an editor

Useful when a client fails silently and you need to know which side is at fault. A successful initialize returns a Mcp-Session-Id header; reuse it on every later call.

Questions that exercise the tools

Use these to demo the surface or to sanity-check that a host is really calling the server rather than answering from training data.

Ask the agentWhat it proves
“Are there any active Azure incidents right now?”Single call to get_active_incidents; returns overall posture plus per-source health
“What is the health of East US 2?”get_regional_health, including events that name the region only in their title
“Is App Service affected anywhere?”lookup_service_region with no region — the service-anywhere scope
“Any planned Azure maintenance coming up?”get_planned_maintenance unscoped
“Which Microsoft tracking IDs are open against my subscriptions?”Data that cannot come from training — tracking IDs are tenant-specific and change daily
“We deploy to East US 2 this afternoon. Anything I should know?”Tool chaining — regional health plus maintenance, selected by the model without being told which tools to use
“Compare Azure OpenAI and App Service — which has more open issues?”Two lookup_service_region calls and a synthesis step
“Draft an ops-channel message summarizing current Azure health.”The realistic end-to-end shape: retrieve, then write
Test the boundary, not just the happy path Ask “is my VM in West Europe down?” The correct answer is that no incident is published for that region — not that the VM is healthy. The aggregator reports what Microsoft has announced; it never probes your workload. If an agent built on these tools tells a user their resource is fine, the integration is wrong even though every call succeeded. The tool responses carry that wording for exactly this reason — do not summarize it away.

11Production hardening

The template is a pilot baseline: managed identity everywhere, no plain secrets, RBAC at the narrowest workable scope, logs to Log Analytics, TLS-only ingress. These are the deltas to close before it becomes a production dependency.

When it misbehaves

?Troubleshooting

SymptomCause and fix
emergingIssues reports 0 Not a fault. Microsoft has published no broad incident. Confirm the source reads ok — that is the health signal, not the count.
emergingIssues reports an auth error The Reader role assignment has not propagated, or AZURE_CLIENT_ID does not match the identity attached to the app. Wait a few minutes, then restart the revision.
serviceHealth is empty SUBSCRIPTION_IDS is unset, or the identity lacks Reader on those subscriptions. Service Health is subscription-scoped by nature.
/api/status/changes returns 503 WATCH_ENABLED is not true. Run azd env set WATCH_ENABLED true and azd provision.
lastDelivery.ok is false Read lastDelivery.status. 401 means a signature mismatch — almost always the receiver re-serializing the body instead of hashing the raw bytes. A timeout means the receiver is doing work before responding.
Every change arrives twice More than one replica is running. Set minReplicas and maxReplicas to 1, or make the subscriber idempotent on id + kind.
Container will not start Usually an image pull failure. Check the revision with az containerapp revision list. The template grants the identity AcrPull, but the assignment can lag the first revision — restart it.
You rotated the secret in Key Vault and nothing changed By design. The container holds its own copy so a first deployment cannot race the Key Vault RBAC assignment. After rotating, run azd env set WEBHOOK_SECRET <new> then azd provision, and update your subscriber at the same time.
The app is still running the placeholder hello-world image azd provision ran but azd deploy did not. Run azd deploy, or azd up to do both.
Remote build fails with archive/tar: write too long The build context is too large or changed while being packed. Keep .dockerignore intact — it excludes node_modules, build output and every directory the API image does not need.
azd deploy cannot find the service The container app is located by its azd-service-name tag, which must match the service key in azure.yaml (api). If the tag was edited, re-run azd provision.
Deployment fails on the Key Vault name Vault names are globally unique and capped at 24 characters. The name carries a hash of the environment name, so a different azd env new name gives a different vault. If you deleted a vault recently, soft-delete is holding the name — purge it or pick another environment name.
